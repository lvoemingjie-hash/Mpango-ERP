## 1. Architecture Decisions

### 1.1 Permission Naming: `finance:read`

**Decision:** Introduce `finance:read` as a new permission code for receivables and financial summary endpoints.

**Justification (by deduction):**
- Existing pattern: `{noun}:{verb}` — e.g. `orders:read`, `payments:create`, `inventory:read`, `dashboards:read` (files: `backend/api/v1/orders.py:20`, `payments.py:8`, `inventory.py:24`).
- Finance is a distinct resource noun (ledger aggregates, not raw orders). Using `orders:read` would over-expose: a user who can see orders doesn't automatically need to see AR summaries.
- Invoice download uses `orders:read` because an invoice is a projection of a single order — same data, different format.

**Reference files:**
- `backend/api/middleware/rbac.py` — `RequirePermission` class
- `backend/api/v1/orders.py` — `RequirePermission("orders:read")`
- `backend/api/v1/payments.py` — `RequirePermission("payments:create")`

### 1.2 Error Code Structure

**Decision:** All new error codes follow the `{"code": "SCREAMING_SNAKE", "message": "..."}` dictionary pattern inside `HTTPException.detail`.

**Justification:**
- Existing codes: `INVALID_ORDER_ID`, `ORDER_NOT_FOUND`, `SKU_NOT_FOUND`, `MISSING_IDEMPOTENCY_KEY`, `IDEMPOTENCY_CONFLICT` (files: `backend/services/payment_service.py:68`, `backend/services/inventory_service.py:25`).
- Frontend `api.ts` interceptor (line 78) already destructures `detail.error.code` and `detail.error.message` for toast rendering.

**New error codes added:**
| Code | HTTP | Usage |
|---|---|---|
| `INVENTORY_SHORTAGE` | 409 | `InventoryService.deduct_stock()` — stock unavailable |
| `STALE_VERSION` | 409 | Future optimistic lock checks |
| `INVOICE_NOT_AVAILABLE` | 422 | Invoice requested for draft/cancelled/voided orders |

### 1.3 Concurrency Control: `SELECT FOR UPDATE`

**Decision:** Use pessimistic row-level locking for inventory deductions.

**Justification:**
- The Kenyan wholesaler use case involves many concurrent mobile sales reps placing orders against the same SKU pool.
- Optimistic locking would require retry loops on the frontend — bad UX on low-bandwidth mobile connections.
- `SELECT FOR UPDATE` in `InventoryService.deduct_stock()` guarantees serialized access per-SKU while keeping the critical section minimal.

**Reference:** `backend/services/inventory_service.py` — `deduct_stock()` method.

### 1.4 Idempotency: Existing Middleware + Service-Level Guard

**Decision:** Leverage existing `IdempotencyMiddleware` for generic protection; keep the service-level `idempotency_key` check in `PaymentService` as a defense-in-depth layer.

**Reference:** `backend/api/middleware/idempotency.py`

### 1.5 Security Hardening: RBAC for Exposed Endpoints

**Decision:** Add explicit RBAC permission guards to three previously under-protected endpoints.

**Justification:**
- **`jobs_test.py`**: All 5 routes had zero authentication. Even though the router is behind `MPANGO_ENV != "production"` in `app.py`, staging/dev environments are still multi-user. Any logged-in user could enqueue arbitrary jobs. Fix: add `RequirePermission("system:admin")` to all routes for defense-in-depth.
- **`metrics.py` `DELETE /`**: The metrics reset endpoint used only `get_current_user_context` — any authenticated user could wipe production metrics. Fix: escalate to `RequirePermission("metrics:admin")`.
- **`exports.py` `POST /`**: The export creation endpoint relied on tenant context extraction but no RBAC check. Any authenticated user in a tenant could trigger unlimited data exports. Fix: add `RequirePermission("exports:create")`.

**New permissions introduced:**
| Permission | Description | Assigned to |
|---|---|---|
| `system:admin` | Full system administration (job queues, debug endpoints) | admin role |
| `metrics:admin` | Reset application metrics | admin role |
| `exports:create` | Request data exports | admin role |

## 3. Evidence of Concurrency Safety

### 3.1 `SELECT FOR UPDATE` Implementation

```python
# backend/services/inventory_service.py — deduct_stock()
result = await db.execute(
    select(InventoryStock)
    .where(InventoryStock.sku_id == sku_id)
    .where(InventoryStock.is_deleted.is_(False))
    .with_for_update()   # <-- Row-level lock
)
```

**Behavior under concurrent requests:**
1. Transaction A acquires lock on SKU "UNGA-2KG".
2. Transaction B blocks on the same row until A commits/rolls back.
3. After A commits, B sees the updated `quantity_reserved` and either proceeds or raises `InventoryShortageError`.

### 3.2 Idempotency Evidence

- **Middleware level:** `IdempotencyMiddleware` (line 55–237) checks `X-Idempotency-Key` header, caches responses per `(tenant, user, method, path, body_hash)`, and returns cached results for duplicate keys.
- **Service level:** `PaymentService.create_payment()` checks for existing payment with same `idempotency_key` and raises `IDEMPOTENCY_CONFLICT` (409) if payload differs.
- **Double ledgering prevention:** Payments that match an existing idempotency key return the original response without creating new ledger entries.

## 4. Evidence of Tenant Isolation

### Finance Endpoints

All three finance endpoints use `get_tenant_db_session` (from `backend/api/dependencies.py`):

```python
@router.get("/receivables", ...)
async def list_receivables(
    ...
    db: AsyncSession = Depends(get_tenant_db_session),  # <-- JWT-derived search_path
):
```

This dependency:
1. Extracts `tenant_schema` from the JWT `TokenPayload`.
2. Sets PostgreSQL `search_path` to the tenant schema.
3. All subsequent queries are scoped to that tenant's data.

**Cross-tenant access is structurally impossible** — there is no URL parameter or header that overrides the schema.

## 5. Evidence of Security Hardening

### 5.1 `jobs_test.py` — Defense-in-Depth

**Layer 1 (app.py):** Router only mounted in non-production environments:
```python
# backend/api/app.py line 110-113
if settings.MPANGO_ENV != "production":
    app.include_router(jobs_test.router, prefix="/api/v1/test/jobs", tags=["jobs-test"])
```

**Layer 2 (route-level):** All 5 routes now require `system:admin`:
```python
# backend/api/v1/jobs_test.py — every handler
async def enqueue_test_email(
    request: EnqueueJobRequest,
    token: TokenPayload = Depends(RequirePermission("system:admin")),
    queue: JobQueue = Depends(get_job_queue)
):
```

### 5.2 `metrics.py` — `DELETE` Escalated

**Before:** Any authenticated user could reset metrics (used `get_current_user_context`).  
**After:** Only users with `metrics:admin` permission:
```python
async def reset_metrics(
    request: Request,
    token: TokenPayload = Depends(RequirePermission("metrics:admin")),
):
```

Note: `GET /metrics` intentionally keeps the lighter `get_current_user_context` guard — reading metrics is non-destructive and useful for monitoring dashboards.

### 5.3 `exports.py` — `POST` Protected

**Before:** Used `_extract_tenant(request)` for tenant isolation but no RBAC check.  
**After:** Requires `exports:create` before tenant extraction even runs:
```python
async def create_export(
    request: Request,
    body: ExportRequest,
    token: TokenPayload = Depends(RequirePermission("exports:create")),
) -> JSONResponse:
```

Note: `GET /exports/{job_id}` and `GET /exports/{job_id}/download` remain protected by tenant-ownership verification — only the tenant that created the export can see/download it.
