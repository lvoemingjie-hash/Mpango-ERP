本文件用于指导Mpango批发零售ERP系统的产品设计与MVP开发，基于Spec-Kit项目规范。

# 一、系统目标与背景

Mpango ERP 是面向非洲市场的批发零售一体化供应链管理系统，旨在帮助批发商实现数字化运营、客户关系管理、库存与采购协同。系统设计遵循多租户隔离、安全高效、可扩展的原则。

# 二、模块一：销售管理（Sales Management）

销售模块为零售商提供下单与订单管理体验，同时为批发商提供订单流转与状态管理。

核心功能：注册登录、商品浏览与搜索、下单支付、订单状态管理。

状态流程：待确认 → 备货中 → 待发货 → 已发货 → 已完成 → 已取消

# 三、模块二：客户关系管理（CRM）

CRM模块帮助批发商建立系统化客户档案，实现客户分级、信用额度与专属定价管理。

新增子模块：批发商邀请与零售商绑定机制，实现一对多或多对多绑定关系。

# 四、模块三：库存管理（Inventory Management）

库存模块实现商品录入、库存同步、变动记录与预警机制。

MVP阶段：商品录入、库存同步、手动调整、库存预警。

未来阶段：AI商品识别导入、供应商数据同步。

# 五、模块四：采购与供应商管理（Procurement）

采购模块构建批发商的上游管理体系，实现供应商维护、采购单创建、收货入库与库存自动更新。

MVP阶段：供应商管理、采购订单、收货入库。

Phase 2：对账与付款管理；Phase 3：智能补货与供应商API同步。

# 六、系统架构与流程

系统架构分为零售商端App、批发商ERP后台、核心服务层三部分。各模块通过API与事件总线实现数据同步。

模块流程：批发商邀请零售商注册 → 零售商下单 → 批发商发货 → 库存变动 → 采购入库补货 → 数据闭环。

# 七、阶段划分

MVP阶段：销售、CRM、库存、采购四个核心模块。
Phase 2：财务对账、赊销账期、智能补货预测。
Phase 3：供应商API集成、BI分析、AI补货。

# 八. MVP详细功能需求

本章节是PRD的核心，将MVP范围内的五个模块分解为具体的史诗（Epic）、特性（Feature）和用户故事（User Story），并提供验收标准（Acceptance Criteria）。

4.1. 模块一：销售管理 (核心)

这是连接批发商和零售商的生命线，是MVP最核心的模块。

史诗 1: 零售商采购流程

目标: 让零售商能够像使用C端电商App一样，轻松、高效地完成采购。

特性 1.1：用户注册与登录（优化版）

目标：
确保零售商账户的注册、登录及关联关系符合批发商主导的业务逻辑，支持多租户隔离和未来扩展。

用户故事

作为一个零售商，我希望能在收到批发商邀请后注册并登录系统，以便访问该批发商的店铺并进行下单。

业务逻辑与规则（修订版）

注册来源

零售商必须通过批发商邀请才能进入系统。

批发商在后台通过手机号发出邀请，系统自动生成并发送邀请链接或验证码。

未受邀的手机号无法注册；输入后提示“请联系您的批发商邀请加入”。

账户绑定关系

一个零售商账号（手机号为唯一标识）可以与多个批发商建立绑定关系。

每个绑定关系均由批发商发起并确认。

不同批发商的数据严格隔离，零售商在App端看到的商品与订单信息仅限于当前选定批发商。

登录方式与验证机制

支持两种登录方式：
a) 用户名 + 密码（传统方式）
b) 手机号 + 验证码登录（便捷方式）

验证码5分钟内有效，连续输错3次后锁定登录10分钟。

后续版本预留社交账号（Google、Facebook）登录能力。

安全与异常处理

每个账号的手机号必须唯一。

验证码请求需频率限制（例如每分钟1次，防止滥用）。

登录后，用户需选择进入哪个批发商的店铺界面（若绑定多个）。

验收标准

批发商能通过手机号成功邀请零售商。

零售商点击邀请链接后，能完成注册并绑定批发商。

未经邀请的手机号无法注册。

零售商可在App中切换不同批发商的店铺视图。

登录系统稳定，认证失败提示友好。

这部分的设计清晰体现了你提到的三点逻辑：

✅ 服务核心是批发商（邀请权在他们手里）；

✅ 支持复杂关系结构（多对多、多对一）；

✅ 数据保护与隔离。

特性 1.2：商品浏览与搜索（优化版）

目标：
为零售商提供清晰、高效、直观的商品浏览与搜索体验，支持多批发商关联情况下的快速定位与切换。

用户故事

作为一个零售商，我希望在App首页看到我所关联的所有批发商，以便快速进入对应店铺浏览商品。
作为一个零售商，当我与多个批发商合作时，我希望能通过搜索或排序快速找到我想访问的批发商。

业务逻辑与规则（修订版）

首页视图（批发商选择页）

App首页展示所有已关联批发商的Logo列表，按名称A–Z排序。

每个批发商以卡片形式展示：Logo、商家名称、所在地（可选）。

用户可在顶部输入批发商名称进行搜索。

点击卡片进入该批发商的店铺主页，展示商品目录。

商品目录页

进入批发商店铺后，展示商品列表（网格或列表视图），包括图片、名称、规格、价格、库存状态。

提供分类导航栏（左侧或顶部Tab），方便按品类浏览。

支持多语言显示（英语、斯瓦希里语）。

商品搜索功能

支持文本搜索（商品名称、条码号、SKU）。

支持模糊匹配。

MVP阶段先上线文本搜索；语音搜索、图片搜索功能接口可预留。

缓存与离线体验

最近访问的批发商店铺及商品数据可在本地缓存。

无网络时，零售商仍可浏览已缓存的批发商商品目录，系统自动在网络恢复后同步数据。

验收标准

首页能展示所有关联批发商，按A–Z排序。

用户可通过搜索快速定位批发商。

点击任一批发商后能加载其商品目录。

离线模式下可浏览已缓存数据。

搜索结果准确，响应时间在3秒内（3G网络环境下）。

特性 1.3：下单与支付（优化版）

目标：
实现零售商在单一批发商店铺中完成下单、支付的闭环流程，确保订单数据清晰归属、库存实时同步，并兼容多种支付方式。

用户故事

作为一个零售商，我希望在浏览批发商商品后，可以将想采购的商品加入购物车、调整数量，并在结算时选择我的支付方式。
我希望每次下单都只对应一个批发商，以保证订单处理和发货的清晰性。

业务逻辑与规则（修订版）

购物车与订单归属

购物车与批发商店铺绑定。

零售商必须进入某个批发商店铺后才能添加商品至购物车。

购物车中商品不可跨批发商混合结算。

当用户切换批发商店铺时，系统自动切换对应购物车数据（或清空未结算的上一个购物车）。

购物车功能

可查看商品图片、规格、数量、单价、小计及总金额。

支持修改数量、删除商品。

自动计算应付金额并在结算时生成唯一订单号。

若商品库存不足，系统应即时提示“库存不足”并限制数量。

支付方式

M-Pesa 集成（MVP重点实现）

调起M-Pesa STK Push接口，用户输入PIN完成支付。

支付完成后订单状态更新为“已支付待发货”。

货到付款 (COD)

批发商后台可设置是否对该客户开放COD。

COD订单创建后状态为“待付款”。

赊销 (Credit)

若批发商为该客户启用赊销额度，结算页显示“赊销支付”选项。

系统校验客户额度余额与订单金额。

超出额度则禁用赊销下单。

地址与配送信息

零售商下单时可选择默认收货地址或新增地址。

允许在订单中备注特殊要求（如“请周三送达”）。

状态流转（订单生命周期）

新建 → 待支付（若COD/赊销） → 已支付待发货 → 备货中 → 已发货 → 已完成/已取消

状态更新需实时同步到批发商后台和零售商App。

验收标准

零售商仅能在单个批发商店铺中下单。

系统禁止跨批发商购物车。

成功下单后生成唯一订单号。

M-Pesa支付接口正常调用并能反馈结果。

COD与赊销订单逻辑独立运行。

状态流转准确，App端与后台同步无延迟。

特性 1.4：订单管理与跟踪（优化版）

目标：
为零售商提供清晰、简洁的订单状态跟踪体验，让其能随时查看订单进度与详情；同时确保批发商后台状态变更能实时同步到App端。

用户故事

作为一个零售商，我希望能在App里查看我下的所有订单，以及每个订单的当前状态，以便知道我的货物是否已经发货或完成。
作为一个批发商，我希望当我更改订单状态（如发货）时，零售商App端能立即更新状态显示。

业务逻辑与规则（修订版）

订单列表与详情

零售商App中有“我的订单”入口，展示该零售商在所有批发商的订单列表。

支持按批发商、下单日期、订单状态筛选。

列表中展示关键信息：

批发商名称

订单号

下单时间

总金额

当前状态

点击订单进入详情页，展示：商品明细、金额明细、收货地址、支付方式、订单备注。

状态展示（MVP简化）

订单状态为以下阶段：

待确认

备货中

待发货

已发货

已完成

已取消

零售商App仅展示状态，不显示司机、路线或实时位置。

后台操作触发状态变更后，应实时同步到零售商端（通过推送或轮询机制）。

取消与修改规则

仅在订单“待确认”阶段可由批发商取消订单。

零售商无法直接取消订单，可通过客服联系批发商。

批发商取消时需填写原因（记录日志）。

数据同步要求

状态更新延迟≤3秒（在网络正常下）。

App端定期刷新订单状态（如每30秒轮询一次）。

验收标准

零售商可查看所有历史订单及状态。

状态信息准确，批发商后台操作能实时反映到App。

无配送详情展示，仅状态字段。

状态流转完整且日志可追溯。

特性 2.1: 订单中心

用户故事 (批发商): 我希望在我的管理后台有一个订单中心，可以集中查看和管理所有零售商提交的订单。（订单的打印？）

验收标准:  

1. 后台有“订单管理”模块。

2. 新订单进入时，有明显的提醒（如数字角标、通知）。

3. 订单列表支持按状态（待确认、待发货等）、客户、时间范围进行筛选和搜索。

4. 列表展示关键信息：订单号、客户名称、金额、下单时间、状态。

特性 2.2: 订单处理与状态变更

用户故事 (批发商): 对于一个新订单，我需要能审核它，确认收款，并更新它的状态，让客户能实时了解进展。

验收标准:  

1. 点击订单可进入详情页，查看所有信息。

2. 订单操作按钮:  

确认订单: 将“待确认”变为“备货中”。

标记发货: 将“待发货”变为“已发货”。此时可填写物流信息（见4.5节）。

确认收款/完成订单: 对于COD或赊销订单，在收到款项后手动完成订单。

取消订单: 可在发货前取消订单，并注明原因。

所有状态变更需要实时同步到零售商的App端。

4.2. 模块二：客户关系管理 (CRM)

模块二：客户关系管理（CRM）优化版

目标：
帮助批发商系统化地管理零售商客户数据，强化客户关系、信用控制与价格策略，实现客户资产数字化与数据隔离。

史诗 3：批发商客户管理

批发商可以集中录入、维护、分类和授权其零售商客户，形成数字化客户档案体系。

特性 3.1：客户信息建档

用户故事

作为一个批发商，我希望能将我的所有零售商客户录入系统并维护档案，以便销售和赊销管理。

业务逻辑与规则

客户档案结构

每个客户以手机号为唯一标识。

核心字段包括：客户名称、联系人、手机号、店铺地址、客户等级、信用额度（如启用赊销）。

可添加标签（如“重点客户”、“新客户”）。

可附加备注字段用于记录客户特性或历史交易备注。

客户录入方式

支持手动新增。

支持批量导入（CSV模板）。

可通过系统自动识别App注册手机号并匹配生成档案。

客户管理权限

仅批发商后台管理员和销售经理有权新增或删除客户。

普通销售人员可查看但不可删除客户档案。

数据安全

客户档案数据为批发商专属，系统在多租户架构下保证隔离。

不同批发商无法访问或导出其他租户客户数据。

验收标准

批发商后台可成功新增、导入、编辑客户。

手机号为唯一标识，重复导入自动识别。

客户档案可按等级、标签、地区筛选。

权限控制正确。

特性 3.2：客户信用与定价管理

用户故事

作为一个批发商，我希望能为不同客户设置赊销额度、还款周期和专属价格，以便灵活地执行不同的销售策略。

业务逻辑与规则

赊销额度设置

每个客户可设定：赊销额度、已使用额度、剩余额度、还款周期。

系统校验赊销使用情况：下单金额不得超过剩余额度。

到期未还款的订单，系统在后台标记“超期”，并限制新赊销下单。

专属价格

可为特定客户或客户等级设置商品专属价格或折扣。

零售商在App端浏览商品时，系统动态返回其专属价格。

若无专属价格，则显示标准售价。

价格优先级规则

若同时存在客户等级价与个人专属价，则优先个人价。

后台可查看所有商品的定价来源逻辑。

信用与价格数据同步

价格与信用额度数据应实时同步至下单模块。

修改客户信用或价格后，次日自动同步App端。

验收标准

批发商能为客户设置赊销额度与还款周期。

系统校验赊销余额正确。

专属价格逻辑准确，App端展示与后台一致。

到期未还款客户自动标记并限制新赊销订单。

模块二：客户关系管理（CRM）

子模块：批发商邀请与零售商绑定机制（新增）

目标：
建立安全、顺畅、自动化的“邀请制绑定”流程，让批发商能够便捷地邀请零售商加入系统，并确保绑定关系的唯一性与数据隔离。

一、业务背景

在Mpango平台中，零售商与批发商的业务关系决定数据访问边界。
为了保证数据安全、客户归属清晰和体验流畅，系统采用 “批发商邀请 → 零售商注册 → 自动绑定” 的机制。
该流程是客户管理（CRM）的基础环节，也与销售模块的登录、店铺访问逻辑紧密相关。

二、用户故事

作为批发商，我希望能够直接邀请我的零售商客户加入平台，让他们通过App完成注册并自动与我绑定。
作为零售商，我希望点击批发商发送的邀请链接后能直接注册并进入该批发商的店铺，无需手动输入邀请码。

三、业务逻辑与规则

1. 批发商邀请

批发商后台提供「邀请零售商」功能。

批发商可选择以下三种方式添加客户：
a) 单个邀请：手动输入手机号；
b) 批量导入：上传Excel模板（系统批量生成邀请码）；
c) 自动识别：匹配历史App注册手机号，直接建立绑定关系。

系统自动生成 唯一的邀请码 + 专属邀请链接（带参数）。

批发商可一键发送邀请短信，短信模板支持本地语言（英语/斯瓦希里语）。

2. 零售商接收与注册

零售商收到邀请短信，点击下载链接后自动进入App。

App识别邀请参数（如 mpango://register?invite=8452&tenant=ABC）。

系统自动填写手机号和邀请码，无需手动输入。

注册完成后，系统自动与对应批发商建立绑定关系。

3. 多批发商绑定机制

一个零售商（手机号为唯一标识）可与多个批发商建立绑定关系。

每个绑定关系由批发商发起，系统自动识别并记录。

零售商进入App首页后，展示其所有已绑定批发商Logo，按A–Z排序。

切换批发商时，App自动加载对应数据与购物车。

4. 安全与数据隔离

每个邀请码和链接仅对目标手机号有效，且有效期为7天。

批发商间客户数据严格隔离，不可跨租户访问。

所有绑定行为均记录日志（时间、邀请人、手机号、状态）。

5. 后台数据同步

零售商注册成功后，批发商后台客户列表实时更新状态为“已注册”。

后台可查看每个邀请的状态（已发送、已注册、未注册、已过期）。

提供“重新邀请”功能，一键重发短信。

四、验收标准

批发商可成功生成邀请码与邀请链接。

零售商点击链接后能自动注册并绑定批发商。

无需手动输入邀请码。

多批发商绑定正常工作，App能展示所有关联批发商。

后台邀请状态更新准确。

数据隔离验证通过（A批发商无法访问B批发商客户数据）。

补充：一个流畅的连接过程，既能让零售商轻松进入系统，又能让批发商牢牢掌握客户关系。

用户故事

作为一个批发商，我希望能随时查看商品库存，系统能在发货、采购等操作时自动调整库存数量，并提供低库存预警，以便我保持合理的备货。

特性 4.1：商品与库存录入

业务逻辑与规则

商品信息结构

每个商品（SKU）应有唯一标识（product_id）。

字段包括：商品名称、条码、规格、单位、分类、品牌、图片、采购价、标准售价、库存数量、库存预警值、状态（上架/下架）。

支持多规格商品（如同一商品有不同包装或尺寸）。

商品录入与导入

支持手动新增单个商品。

支持通过Excel模板批量导入商品与初始库存。

系统校验重复SKU与条码，避免重复导入。

库存初始设置

新商品录入时必须设置初始库存。

系统可选地支持“无库存不允许上架”规则。

批发商可设置库存预警阈值（例如低于10件时提醒）。

商品状态

可切换上架/下架状态。

下架商品在零售商端不可见。

验收标准

批发商可成功新增商品并录入初始库存。

重复SKU校验正确。

库存预警触发逻辑准确。

下架商品在App端不展示。

特性 4.2：库存变动与同步

用户故事

作为一个批发商，我希望系统能自动处理因销售、发货、采购、退货造成的库存变动，并能记录每次调整的明细。

业务逻辑与规则

库存自动变动逻辑

当销售订单状态从“待发货”变为“已发货”时，系统自动扣减库存。

当采购订单执行“收货入库”时，系统自动增加库存。

当订单被取消（未发货）时，系统自动回补库存。

手动库存调整

批发商可手动调整库存（例如盘点差异、损耗、退货）。

调整需填写原因（下拉选项：盘盈、盘亏、退货、损耗等）。

所有调整操作应记录在库存日志中（记录操作人、时间、原因、调整数量、调整后库存）。

库存流水与追溯

系统自动生成库存流水记录：

变动来源（销售订单、采购订单、手动调整）

商品ID

数量变化（正负）

操作时间、操作人

库存日志支持筛选与导出。

库存同步

每次库存变动实时同步至零售商App（显示当前可售数量）。

当商品库存为0时，App端自动标记“缺货”并禁用“加入购物车”。

同步延迟不得超过3秒。

验收标准

销售、采购、取消操作能自动调整库存。

手动调整日志完整可追溯。

App端商品库存展示与后台一致。

缺货商品无法下单。

特性 4.3：库存预警与通知

用户故事

通知机制

支持邮件/短信/系统通知提醒。

后续版本可接入自动补货建议（基于销售数据预测）。

权限与视图

管理员与采购经理可查看预警看板。

普通销售人员仅能查看库存状态，不接收通知。

验收标准

系统可正确识别低库存商品。

预警看板实时更新。

通知推送准确无延迟。

1️⃣ 动态字段定义系统（MVP阶段实现）

每个商品由两部分构成：

核心字段（系统统一）：name, sku, unit, category, price, status, image_url

自定义字段（批发商自定义）：如“品牌”、“颜色”、“规格”、“型号”等。

自定义字段以JSON结构存储在数据库中，可动态扩展。

商品录入时，系统根据批发商定义的模板自动生成对应表单。

自定义字段影响前端显示和搜索筛选逻辑。

✅ 验收标准：

批发商可创建并保存自定义字段模板；

录入页面动态渲染字段；

商品数据结构可兼容多租户差异。

2️⃣ 批量导入与数据校验（MVP阶段实现）

系统提供标准Excel模板（含核心字段与自定义字段）。

支持单次导入5000条SKU（异步处理）。

系统自动校验：

SKU重复；

字段缺失；

数据格式错误；

导入后生成导入报告（成功数、失败原因）。

支持批量更新价格与库存。

✅ 验收标准：

导入文件字段匹配正确；

系统能识别错误并给出提示；

成功导入的商品即时可用。

3️⃣ AI辅助录入（未来阶段 Phase 2）

批发商可上传商品图片、目录PDF、或Excel商品清单；

系统通过AI识别商品名称、品牌、条码、包装规格等字段；

自动生成SKU并匹配到对应分类；

若字段缺失，系统自动提示补全建议。

支持批量处理（每次不超过100条识别任务）。

🧩 设计说明：

该功能将使用AI文本与图像识别（OCR+NLP）模型；

识别结果需人工确认后生效（避免误差传播）。

⚠️ 非MVP阶段实现，建议在Phase 2引入，以提高批量录入效率。

4️⃣ 上游供应商数据同步（未来阶段 Phase 3）

批发商可一键从供应商目录同步商品数据（含SKU、图片、价格、库存）；

支持变更检测（系统对比供应商数据与本地SKU差异）；

批发商可选择自动更新或人工确认后更新；

同步记录存入日志表，支持回溯。

🧩 接口说明（预留）：

POST /api/v1/supplier/import_catalog

GET /api/v1/supplier/sync_status

数据结构遵循通用 ProductSchema 模型。

无法追踪采购历史与供应商表现。

该模块的核心目标是：

“把供应商、商品、库存、资金流串成一条清晰的链条。”

创建采购单 → 供应商确认 → 收货入库 → 订单完成

对账报表导出；
