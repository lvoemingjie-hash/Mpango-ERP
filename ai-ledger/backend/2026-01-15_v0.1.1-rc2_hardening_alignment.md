## P0 — Idempotency hardening

### What changed

- `backend/api/middleware/idempotency.py`
  - Cache key now includes:
    - `tenant_schema`
    - `user_id`
    - `HTTP method`
    - `path`
    - `request body hash`
    - `X-Idempotency-Key` (client-provided)
  - Added a storage abstraction (`IdempotencyStore`) and a default `InMemoryIdempotencyStore`.
  - The middleware no longer relies on module-global in-memory state.
  - Reads request body once, computes `body_hash`, then re-injects body back into the ASGI request receive channel for downstream handlers.
  - Tenant/user are extracted best-effort from the `Authorization: Bearer ...` header by decoding JWT; failures fall back to `anonymous` namespace.

- `backend/tests/test_idempotency.py`
  - Updated self-contained cache key tests to match the new key shape and to assert that tenant/user/body changes produce distinct keys.

### Before (risk)

- Cache key was based on `{idempotency_key}:{method}:{path}`.
- In-memory cache was a **process-global dict**, shared across all tenants/users.
- Collision risks:
  - Cross-tenant replay or conflict if two tenants reuse the same idempotency key on the same endpoint.
  - Cross-user replay/conflict within a tenant.
  - Same key but different request payloads could incorrectly replay cached responses.

### After (risk reduced)

- Cache keys are namespaced by tenant + user and bind to the exact request body hash.
- Cross-tenant / cross-user collisions are prevented by construction.
- Store abstraction prepares for Redis without reworking middleware logic.

## P1 — Dependency & Docker alignment

### What changed

- `backend/pyproject.toml`
  - Added Poetry sections (`[tool.poetry]`, `[tool.poetry.dependencies]`, and groups).
  - Switched build backend to `poetry-core`.
  - Removed duplicate PEP621 dependency lists to avoid ambiguity.

- `backend/poetry.lock`
  - Added (generated) lock file to provide reproducible builds.

- `backend/Dockerfile`
  - Docker now installs dependencies via `pyproject.toml + poetry.lock` using Poetry.
  - Keeps non-root user.
  - Adds `curl` and a container `HEALTHCHECK` hitting `/health`.

### Before (risk)

- `requirements.txt` and `pyproject.toml` co-existed; Docker installed from `requirements.txt`.
- This allows environment drift (dev uses pyproject ranges, container uses pinned requirements).

### After (risk reduced)

- Poetry + lock file is the single source of truth.
- Container installs are reproducible and aligned with local dev.

## P1 — Pricing contract clarity

### Decision

**Rule B**: `unit_price` is **client-submitted and validated**.

Rationale (no UI contract change): current frontend order creation requires users to input `unit_price` and sends it in the payload.

### What changed

- `docs/contracts/openapi.yaml`
  - `OrderItemCreate` now requires `unit_price`.

- `backend/schemas/order.py`
  - `OrderItemCreate` now includes required `unit_price: Decimal` with `ge=0` validation.

- `backend/api/v1/orders.py`
  - Order creation now passes `unit_price` into the CRUD layer.

### Before (risk)

- OpenAPI & backend request schema did not include `unit_price`.
- API layer dropped `unit_price` on write.
- CRUD defaulted to `10.00` if `unit_price` missing.
- This could cause pricing disputes and data integrity issues.

### After (risk reduced)

- OpenAPI, backend validation, and persistence logic are aligned.
- Server still calculates totals and subtotals (business behavior preserved), but uses the client-provided unit_price.

## v0.1.1-rc2 Follow-up — Tenant bypass removal + Compose healthchecks

### 1) Remove deprecated header-based tenant selection

**Change**:

- `backend/api/dependencies.py`
  - Removed `get_tenant_session()` which allowed selecting tenant schema from `X-Tenant-Schema` header.

**Before (risk)**:

- Even though marked DEPRECATED, the function provided a potential future bypass path for tenant isolation (human error / copy-paste risk).

**After (risk reduced)**:

- Tenant schema can only be derived from JWT context (`get_tenant_db_session`), aligning code with the multi-tenancy contract.

### 2) Add docker-compose healthchecks and health-based dependency ordering

**Change**:

- `docker-compose.yml`
  - Added healthchecks for:
    - `postgres` via `pg_isready`
    - `redis` via `redis-cli ping`
    - `backend` via `GET /health/ready`
  - Updated `backend.depends_on` to use `condition: service_healthy` for postgres/redis.

**Before (risk)**:

- `depends_on` only ensured container start order, not readiness; backend could start before DB/Redis were accepting connections.

**After (risk reduced)**:

- Startup ordering is now based on service readiness, reducing flakiness and improving operational reliability.
