## 3. PRICING-R0 冻结输入

### 3.1 三层价格模型

1. **SKU 基础价格**：批发商只需设置一次，作为未配置特别价格时的默认售价。
2. **客户特别价格**：按批发商、零售商和 SKU 覆盖基础价格，不影响其他客户。
3. **订单价格快照**：保存提交价、批发商调整价和最终成交价；历史快照永久不可变。

当前有效价格解析顺序为：

`客户特别价格 > SKU 基础价格`

本订单调价只影响当前订单。不得隐式修改 SKU 基础价格或客户特别价格；将成交价
保存为长期客户特别价格必须是单独、明确且有独立权限的动作。

### 3.2 再次下单

1. 历史订单提供“再次下单”入口，复制供应商、SKU、数量和包装单位，生成新草稿。
2. 历史成交价仅作为比较依据，不作为新订单的权威价格。
3. 服务端按当前客户特别价格或基础价格重新计价。
4. UI 必须逐行显示“上次价格、当前价格、差额”。
5. 停售、不可售、包装变化、数量规则变化或库存不足的商品必须明确提示，不能静默删除。
6. MVP 不默认提供历史价格保证；未来如需价格保证，必须是带有效期的显式批发商政策。

### 3.3 批发商订单调价

1. 零售商提交后，批发商可以原价接受、提出一次正式调价、调整可供数量或拒绝订单。
2. 调价必须逐行记录原价、新价格和原因，原始提交快照不得覆盖。
3. MVP 每张订单只允许一个正式调价版本，不支持多轮议价。
4. 调价发布后订单进入 `AWAITING_RETAILER_CONFIRMATION`，批发商不能继续修改该版本。
5. 零售商拒绝后订单进入 `CANCELLED_RETAILER_REJECTED`。
6. 已锁价、已付款、已出库或已开票订单禁止直接改价；后续只能取消重建，退款/补款/贷项流程另行设计。

### 3.4 用业务动作完成确认

调价后的页面不增加孤立的“接受”步骤，提供三个清晰动作：

- `接受并付款`：锁定当前订单版本并进入 `PAYMENT_PENDING`；随后选择现金、转账或移动支付。点击按钮本身不得把订单标记为已付款。
- `接受并使用信用额度`：实时检查授信、可用额度和逾期限制；成功后占用额度并进入 `CONFIRMED_ON_CREDIT`。
- `拒绝并取消订单`：进入 `CANCELLED_RETAILER_REJECTED`。

信用额度不足时不得自动取消或视为已经接受；订单继续等待确认，零售商仍可付款或拒绝。

### 3.5 24 小时超时

1. 24 小时从批发商发布调价时开始，不从最初下单时间开始。
2. 服务端保存 `price_confirmation_expires_at`，UI 显示倒计时和绝对截止时间。
3. 到期未处理进入 `CANCELLED_PRICE_CONFIRMATION_EXPIRED`。
4. 即使后台任务延迟，服务端也必须拒绝截止时间后的付款或信用接受请求。
5. 自动取消必须释放库存预留、信用额度占用和未完成付款意图。
6. 接受、拒绝和超时必须绑定订单版本并支持幂等，旧页面不得接受旧价格。
7. 批发商原价接受时，零售商最初提交已代表接受该价格，不需要再次确认。

## 4. PRICING-R0 必须产出的测试矩阵

至少覆盖以下场景：

1. 无特别价格时使用 SKU 基础价格。
2. 指定零售商使用特别价格，其他零售商仍使用基础价格。
3. 跨租户同 SKU 或同零售商标识不得串价。
4. 历史订单快照在基础价和特别价变化后保持不变。
5. 再次下单重新计价并显示价格差异，不继承临时历史折扣。
6. 批发商原价接受不要求零售商重复确认。
7. 调价后付款行为原子地接受正确订单版本，但不伪造已付款。
8. 信用接受在额度充足时成功，在额度不足时保持待确认。
9. 拒绝立即取消，重复拒绝保持幂等。
10. 24 小时边界前可接受，边界后 fail closed 并自动取消。
11. 双击付款、信用接受或拒绝不得产生重复订单、支付、应收或库存动作。
12. 已付款、已出库和已开票订单的调价请求必须被拒绝。

  AUDIT_ONLY_NON_BLOCKING`，不阻塞 MVP）。

上述后置范围不得阻塞基础价格、客户特别价格、一次性订单调价和再次下单的 MVP 闭环。
