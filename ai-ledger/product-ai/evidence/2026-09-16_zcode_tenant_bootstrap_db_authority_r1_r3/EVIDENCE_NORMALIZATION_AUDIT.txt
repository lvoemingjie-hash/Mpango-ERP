EVIDENCE NORMALIZATION AUDIT — MPANGO_TENANT_BOOTSTRAP_DB_AUTHORITY_R1_R3
============================================================================

WHY THIS FILE EXISTS
--------------------
The harness writes its evidence as plain text/JSON. The repository's NORMAL
pre-commit hooks (`trailing-whitespace`, `end-of-file-fixer`) normalized
trailing whitespace / the end-of-file newline of that text evidence at commit
time. No hook was bypassed (no --no-verify), no evidence file was hand-edited,
and no evidence content was rewritten by hand. This audit records, with facts
that are recomputable from this repository, that the normalization is
semantic-free.

VERIFIABLE FACTS
----------------
1. COMMITTED DIGESTS. The committed evidence files and their sha256 values are
   listed below; `sha256sum <file>` in this directory reproduces each value.

2. REPORT: EXACTLY ONE ADDED END-OF-FILE NEWLINE. The as-generated (pre-hook,
   on-disk) digest of the machine report was recorded at first validation,
   before any git operation was run:
       harness_report.json as-generated
         = 2a6a7344e5e202a8068c88c5c1e105a0a484753efef7aa7b47b1e69b3371d78d
   Taking the committed bytes and removing the single final newline reproduces
   that digest exactly; every other candidate transformation (CRLF conversion,
   an extra blank line, preserved trailing spaces) produces a different digest.
   So the report's committed form differs from the generated form by exactly
   the end-of-file-fixer's one trailing newline.

3. REPORT SEMANTICS UNCHANGED. The committed report is identical to the
   generated report after JSON parsing, and the post-normalization report was
   re-validated against the R1-R3 identity gate: task and authorization are
   R1-R3, verdict PASS, eight mutations all RED, MM8 7/7 named REDs,
   synthetic-secret scan 0 of 19.

4. CROSS-CONSISTENCY OF THE COMMITTED EVIDENCE — 28/28 checks PASS, run against
   the COMMITTED bytes:
   - every suite run's reported rc equals the `rc=` header of its committed log
     (6/6 suites, all rc=0);
   - every mutation's reported FAILED nodeids, and every declared named-RED
     nodeid, appear as `FAILED <nodeid>` in that mutation's committed log
     (MM1-MM8, including MM8's 7/7);
   - the committed verify logs carry rc=0 (intact database) and rc=2
     (runtime-owned-guard counterexample);
   - the report's pre-run and restored script digests equal the current
     working-tree bytes of both scripts, and those bytes are LF-normalized
     identical to the committed blobs of implementation candidate
     a21878c1 — i.e. every mutation restore returned the scripts to exactly
     the candidate bytes.

5. SCOPE OF THE NORMALIZATION. Observed at commit time through the failure of
   the first commit attempt plus `git diff` between the staged bytes and the
   hook-normalized bytes: removals are limited to trailing whitespace on a
   line, including whitespace-only lines (e.g. pytest `--tb=short` padding
   "E     " -> "E", "  " -> ""), collapsed to a single end-of-file newline. No
   line was added, removed or reordered apart from that trailing blank-line
   collapse; no assertion, count, digest, identity field, verdict or
   secret-scan result changed.
